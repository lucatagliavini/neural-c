# Session handoff — Milestone 9.3 shuffle feasibility confirmed

## Session result

- The deterministic shuffle design was evaluated before production changes.
- Absolute-epoch derivation is sufficient for exact resume. No mutable shuffle
  PRNG state or materialized sample-order plan needs to be added to checkpoint
  payloads.
- Milestone 9.3 can proceed once the user confirms implementation.
- No production source, public header, authoritative contract, or persistence
  format was changed. The experiment lives only under ignored `build/`.
- The user-owned untracked `projects/flower3/` directory remains untouched.

## Proposed deterministic contract

- Treat the existing zero-based trainer `epoch_index` as the shuffle epoch
  identity. At a resume boundary, the first regenerated plan therefore uses
  `epoch_index == completed_epochs`.
- Derive a local epoch seed from the training seed and absolute epoch with only
  defined `uint64_t` arithmetic:

  ```text
  domain = 0x6e657572616c2d73
  epoch_seed = splitmix64_mix(
      (training_seed XOR domain) +
      0x9e3779b97f4a7c15 * (epoch_index + 1))
  ```

  The fixed domain separator must be retained as part of the public contract.
  For a fixed training seed, the odd increment, addition, and SplitMix64 mixer
  are bijections over 64 bits, so distinct representable epoch identities
  derive distinct epoch seeds.
- Initialize an epoch-local SplitMix64 stream from that seed. Do not read or
  modify `NeuralModel.random_state`; its persisted `rng_state` continues to
  describe model initialization provenance only.
- Initialize the plan to source indices `[0, sample_count)`, then run descending
  Fisher-Yates. For bound `b`, reject 64-bit draws below
  `(0 - b) % b`, then use `draw % b`. This removes modulo bias using portable
  C11 unsigned arithmetic and needs no 128-bit compiler extension.
- Mini-batches are contiguous slices of logical positions in the shuffled
  plan. Worker count controls scheduling only. Gradient accumulation follows
  increasing logical plan position, not increasing source index.
- Fresh, resumed, and additional training use the same absolute-epoch mapping.
  A hard failure inside an epoch can repeat the complete plan from the prior
  checkpoint boundary without persisting partial shuffle state.

## Experiment and evidence

- `build/shuffle_epoch_experiment.c` exercises seed 42, 17 samples, 257 epochs,
  batch size 5, and logical worker counts 1 and 4.
- It verifies repeated-plan identity, valid permutations, distinct consecutive
  epoch plans, continuous versus split-at-epoch-113 generation, stable logical
  order across worker counts, and the incomplete final batch.
- Native x86-64 and QEMU-emulated ppc64le output was byte-identical:

  ```text

  series_hash 0d4b6f7e007749c5
  resume_hash 0d4b6f7e007749c5
  ```

- Both output files have SHA-256
  `c4ed46e4cb3294f66ec6b209d25eb946a8f29b928e679e8883627732701538b2`.
- The experiment compiled with strict warnings as errors on both targets.
  Native AddressSanitizer and UBSan passed with leak detection disabled, matching
  the repository's sandbox-compatible sanitizer convention. LeakSanitizer alone
  cannot run under the environment's ptrace wrapper.

## Persistence and compatibility decision

- Keep weights/checkpoint versions 1 and 2 unchanged because the epoch plan is
  a pure function of digest-bound configuration plus absolute epoch.
- Shuffle enablement must be explicit training-owned configuration and covered
  by the canonical training digest. The recommended compatibility rule is that
  absent/disabled shuffle preserves the legacy canonical stream exactly, while
  enabled shuffle appends a versioned shuffle marker/algorithm identity.
- Changing shuffle enablement must invalidate existing persistence before model
  mutation. The training seed is already digest-owned.
- Do not change or reuse `data_import.c`'s historical modulo-based split
  shuffle: changing it would alter persisted preprocessing version 1/2 split
  semantics. Milestone 9.3 should introduce a separate unbiased helper/contract.

## Implementation impact and next action

- The current executor and accumulator assume contiguous increasing source
  indices. Implementation must distinguish logical plan position from dataset
  sample index, dispatch the latter, and reduce gradients by the former.
- Allocate one `size_t[sample_count]` plan per training run and regenerate it
  in place once per executed epoch. No per-worker plan and no checkpoint copy is
  needed.
- Before coding, finalize the configuration spelling and CLI/init behavior. A
  compatibility-preserving opt-in such as `shuffle 0|1`, with absent/zero
  retaining source order, is recommended.
- Then implement native deterministic tests first, followed by resume,
  thread-count, incomplete-batch, persistence/digest, malformed-input, and
  bidirectional cross-runtime coverage required by the roadmap.
