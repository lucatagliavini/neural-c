# Milestone 5 Proposal — 2026-08-03

## Objective

Make long-running training recoverable and complete the continuation modes
already reserved by the CLI and persistence formats. Preserve deterministic
results across worker counts, epoch-boundary checkpoint semantics, and atomic
file updates.

## Proposed Checkpoints

### 5.1 — Periodic Checkpoint Infrastructure

- Extend epoch observation so project training can persist state every
  `checkpoint_interval` completed epochs.
- Write `checkpoint.txt` atomically with canonical project digests, completed
  and target epochs, optimizer identity, RNG state, and model parameters.
- Keep the trainer independent of filesystem policy: the project layer owns
  checkpoint decisions and persistence.
- Test interval boundaries, write failures, unchanged prior checkpoints, and
  deterministic payloads.

### 5.2 — Resume and Finalization

- Implement `train <project> --resume` using the existing checkpoint parser.
- Validate version, dimensions, digests, optimizer, and epoch bounds before
  modifying the model.
- Continue from `completed_epochs` to `target_epochs`, allowing a different
  execution-only thread count.
- On success, atomically write `weights.txt` before removing `checkpoint.txt`.
  If both files exist after interrupted finalization, validate and complete the
  transition safely.

### 5.3 — Graceful Interruption

- Install minimal `SIGINT` and `SIGTERM` handlers that only set a
  `volatile sig_atomic_t` stop request.
- Observe the request at epoch boundaries, save one valid checkpoint, and exit
  with a documented non-success status.
- Never perform allocation, logging, locking, or file I/O inside a signal
  handler.
- Add subprocess tests that interrupt training and successfully resume it.

### 5.4 — Additional Epochs

- Implement `train <project> --additional-epochs N` from validated
  `weights.txt`.
- Reject refinement while `checkpoint.txt` exists.
- Reset run/optimizer state and target exactly `N` additional epochs while
  retaining total completed-epoch provenance in final weights.
- Test invalid state combinations, zero/overflow values, and deterministic
  equivalence where the training semantics permit it.

### 5.5 — Prediction CLI

- Add the missing inference workflow so the framework fulfills the original
  generate/train/use objective.
- Load and validate `weights.txt` against the project digests before inference.
- Define a versioned text input/output contract and support deterministic
  execution through `--threads` where useful.
- Cover malformed inputs, provenance mismatches, multiple samples, and the XOR
  end-to-end result.

## Supporting Engineering Work

- Add GitHub Actions for native `make check`, sanitizer-compatible tests, and
  the ppc64le cross-build.
- Add coverage reporting or at least a reproducible local coverage target.
- Decide whether fresh/resume/refinement operations need a project lock to
  prevent concurrent processes from racing over persistence files.
- Keep actual ppc64le runtime validation in Milestone 6; cross-compilation alone
  is not sufficient evidence of runtime correctness.

## Recommended Starting Point

Begin tomorrow with checkpoint 5.1 only. First define the checkpoint observer
contract and failure semantics in `docs/training-engine.md` and
`docs/training-resume.md`; then implement persistence integration and focused
tests before introducing signals or resume state transitions.
